# 同见 CMS V1 学习指南

这份指南面向第一次接触内容管理与平台治理的开发者。它不只是介绍后台页面怎么使用，更重要的是解释：为什么同见的 CMS 不能被当成一组“编辑数据库记录”的表单，以及每个治理概念在当前代码和 schema v5 中落在哪里。

配合阅读 [`cms-technical-design.md`](cms-technical-design.md) 效果最好。技术设计给出精确约束，本指南负责解释这些约束背后的理由。

## 1. CMS、CRUD 后台和治理系统有什么不同

普通 CRUD 后台围绕四个动作展开：创建、读取、更新、删除。它适合维护低风险资料，例如修改分类的显示名称或排序。只要权限正确，管理员把一列从 A 改成 B 通常就足够了。

平台治理系统面对的却是有争议、会并发、需要解释和可能被推翻的决定。例如“隐藏一个视频”至少涉及这些问题：

- 谁提出了问题，工作人员为什么有权处理？
- 当时视频处于什么状态，作者是否已主动撤回？
- 决定的公开理由和内部调查材料分别是什么？
- 两名工作人员同时操作时，谁的决定有效？
- 作者如何收到通知、如何申诉、由谁复核？
- 日后怎样证明系统没有把技术验证失败伪装成违规？

因此同见只把少量分类和标签操作看作普通资料维护。案件、内容决定、账号状态、申诉、私密媒体授权和任务重试全部通过“领域命令”完成，不开放任意字段更新 API。

可以把两者的差别记成一句话：CRUD 关心“这行现在是什么”，治理系统还必须回答“为什么变成这样、谁使它变化、依据哪个旧状态、能否复核”。

## 2. 一条治理闭环由哪些部分组成

同见 V1 的最小闭环是：

```text
成员举报或工作人员主动调查
        ↓
moderation_cases 案件：open → in_review → resolved
        ↓
工作人员作出内容或账号决定
        ↓
事实表更新 + moderation_actions + audit_events + 系统通知
        ↓
受影响成员在期限内提交 appeals（pending）
        ↓
非原操作者优先认领（in_review）并复核：upheld 或 overturned
```

这里有三个容易混淆的记录：

- `moderation_cases` 是调查容器，回答“正在处理什么问题”。一个案件恰好指向一个视频或一条讨论。
- `moderation_actions` 是已经作出的治理决定，回答“平台做了什么”。动作只追加，不用新值覆盖旧决定。
- `audit_events` 是后台操作轨迹，范围比审核动作更广。再认证、角色变化、任务重试和私密媒体授权也要审计。

案件可以判定“无违规”。这仍是一个有价值的治理结果，因为举报人需要得到结果，平台也需要避免同一问题被当作从未处理过。案件的公开说明主要给举报人；若工作人员另外对内容作出隐藏、移除或恢复决定，受影响作者收到的是该 `moderation_actions.public_reason`。

## 3. 状态机：先限定允许的变化

状态机不是画图装饰，而是对“下一步允许做什么”的明确限制。没有状态机时，通用编辑器可能把一个已结案件重新改回开放，把作者主动删除的讨论恢复，或把尚未验证的视频直接发布。

### 案件状态

案件只允许：

```text
open → in_review → resolved
```

只有未分配的 `open` 案件可被认领，认领使它进入 `in_review` 并产生一名当前负责人。这不只是界面上的“负责人”标签：只有该人可以追加案件备注、对目标执行隐藏/移除/恢复、申请私密媒体授权或结案。当前负责人可以转交，管理员也可以介入把案件转给另一名有效工作人员；但管理员并不因角色更高就能跳过认领直接记备注、审核内容、读取私密媒体或结案。独立性按目标计算，而不是只检查当前案件：工作人员不能为自己的内容创建主动调查、认领或处理案件，也不能把案件转给目标作者；只要曾举报某视频或讨论，就不能再借另一条举报或主动调查案件处理同一目标。

结案必须选择 `violation_confirmed` 或 `no_violation`，并填写举报人可以看到的公开说明。“无违规”不能与“目标仍被隐藏/移除”同时存在，因此负责人必须先用正常审核命令把目标恢复为 `visible`。内部备注保存在 `case_notes`，不会出现在成员页面。内容作者是通过实际审核动作的公开理由和系统通知获知决定，不会看到案件内部材料。

### 视频状态

视频至少同时具有四个互不替代的维度：

- `validation_status`：媒体管线是否成功验证。
- `visibility`：作者选择公开、未列出或私密。
- `withdrawn_at` / `deleted_at`：作者是否撤回或永久删除。
- `moderation_status`：平台治理维度的 `visible | hidden | removed`。

CMS 的恢复只把 `moderation_status` 恢复为 `visible`。它不会清除作者撤回，不会把私密改成公开，也不会把 `validation_failed` 改成 `ready`。

### 讨论状态

`discussions.deleted_at` 表示作者主动删除，`discussions.moderation_status` 表示平台治理。审核隐藏时公开页显示“正在审核”占位；规则移除时显示中性墓碑；两种状态都保留回复树。CMS 还能在详情页中读取原文以供复核，但作者已删除的讨论没有新的审核写入或恢复入口。

### 账号状态

V1 只允许 `active ↔ suspended`。暂停账号仍能用密码登录，以查看决定、修改密码、退出和申诉，但不能上传、投票、讨论、修改资料或进入 CMS。`disabled` 是终止账号的状态，V1 后台没有把账号设为 disabled 的动作。

### 申诉状态

申诉只允许 `pending → in_review → resolved`。提交申诉不会自动把任何打开页面的工作人员变成复核人；有权者要以当前版本显式认领，使申诉进入 `in_review` 并写入 `reviewer_user_id`。之后只有这名当前复核人能提交 `upheld` 或 `overturned`。当前复核人或管理员可以转交给另一名合格、独立的复核人，但申诉人绝不能复核自己的申诉。若撤销时发现目标已有后续变化，申诉留在 `in_review` 并标记状态冲突，不能把旧决定强行覆盖到新事实上。当前复核人需要再用申诉版本和目标版本双重 CAS，明确选择恢复原动作前状态，或保留当前的后续状态，才能完成人工冲突处理。

## 4. 领域命令：表达意图，而不是暴露列

`UPDATE videos SET moderation_status = ?` 只表达了数据库变化，没有表达治理意图。领域命令则使用“隐藏视频”“结案”“撤销会话”“合并标签”这样的业务语言，并集中执行所有前置条件和副作用。

同见的映射是：

| 层次 | 本项目位置 | 职责 |
| --- | --- | --- |
| HTTP 表单 | `src/governance-routes.js`、`src/cms.js` | 解析请求、CSRF、PRG 303、把领域错误映射为 HTTP 状态 |
| 权限 | `src/cms-auth.js`、`src/governance.js` | 固定 RBAC、账号状态和 CMS 再认证 |
| 领域命令 | `src/governance.js` | 校验状态机、理由、版本、操作者与目标关系 |
| 事务适配器 | `src/governance-store.js` | 在 SQLite `BEGIN IMMEDIATE` 中修改事实并追加记录 |
| 迁移与现有数据入口 | `src/database.js` | schema v5、原有视频/讨论/账号查询以及治理存储装配 |

路由也使用动作语义，例如 `POST /cms/videos/:id/hide`、`POST /cms/cases/:id/claim`，而不是 `PATCH /cms/tables/videos/:id`。这种设计让“后台不能做什么”也可以由服务端代码和测试明确证明。

## 5. RBAC、最小权限和二次认证

RBAC 是“基于角色的访问控制”。同见把权限映射固定在代码中，不提供动态权限编辑器：

- `member` 可以举报可见内容，并对涉及自己的决定申诉。
- `moderator` 可以处理案件、审核视频和讨论，并在案件内申请私密媒体授权。
- `administrator` 继承审核能力，另外管理账号、角色、分类标签、任务，以及除本人利益冲突对象外的全量审计。

最小权限意味着一个人只获得完成工作所需的能力。审核员不需要修改角色或重试系统任务，因此这些功能只给管理员。审核员的工作台可以显示验证失败视频的必要内容摘要，并跳到筛选后的 CMS 视频列表，但没有任务重试入口；对删除队列则只显示匿名失败总数，不传递任务目标、文件名、错误或链接。完整 `/cms/tasks` 和两类重试都只给管理员。申诉也按目标分权：视频和讨论决定可由审核员或管理员复核，账号暂停只由管理员查看、认领和复核；无论角色多高，申诉人都不能复核自己的申诉。反过来，管理员也不能绕过案件负责人、媒体验证器或立即删除视频文件。

这里还有一层“工作人员也是成员”的隔离。隔离按实际治理目标统一计算：本人创作的内容、本人视频所承载的讨论、本人申诉、本人账号，以及工作人员曾举报的视频或讨论都不会因为其角色提升而变成可处理对象；举报过某位作者内容的管理员也不能进入或治理该作者账号。案件、内容、账号、申诉、工作台近期动作和审计查询都会应用同一边界，筛选条件不能取消它。相关详情按 404 处理，伪造写请求按 403 拒绝；讨论详情仍保留回复树结构，但涉及本人或本人举报的节点会遮蔽正文、作者、状态和链接。底层 `audit_events` 仍完整追加，这只是查看边界；否则内容作者或举报人可能从案件与操作者字段反推出受保护身份或证据。

CMS 使用现有账号会话，但进入后台前还要重新输入密码。成功后只更新属于当前工作人员的当前 `sessions.cms_verified_at`；有效时间由 `CMS_REAUTH_MINUTES` 配置，默认 30 分钟。密码复核尝试还会像登录一样受冷却限制：应用同时按工作人员账号和受信的来源 IP 计算，冷却时长复用 `AUTH_COOLDOWN_SECONDS`，状态仅保存在当前进程内。它降低了用户离开已登录设备后后台被直接使用的风险，也把高权限窗口限制在单个会话，而不是整个账号。

角色和账号状态每次请求都从数据库读取。撤销审核员角色后，即使其 Cookie 和再认证时间仍有效，旧会话也不能继续进入 CMS。管理员还不能暂停或降级自己；系统不会允许暂停、降级或通过公开自助注销删除最后一名有效管理员。

## 6. 公开理由、内部备注和隐私边界

治理信息不能因为“管理员看得到”就混在一个文本框里：

- 案件的 `public_explanation` 面向举报人，审核动作的 `public_reason` 面向受影响成员；它们都应能解释规则依据，但不暴露举报人、工作人员或敏感证据。数据库和 `/account/reports`、`/account/appeals` 保留最多 2,000 个 Unicode 字符的完整公开值；既有通知表只保存前 1,000 个字符作为提示预览，不能把通知正文当成公开理由的事实来源。
- 内部备注面向工作人员，用于调查线索、交接和复核。
- `before_json` / `after_json` 只保存治理相关字段，不保存密码散列、Cookie、CSRF、完整媒体或无关个人资料。

私密、未列出、作者撤回或审核隐藏/移除的视频，在 CMS 列表中也只显示必要元数据和占位封面。工作人员必须先认领关联案件，或先填写理由创建主动调查案件再认领。只有 `in_review` 案件的当前负责人可以授权自己的当前会话；授权表单还携带案件 `expectedVersion`，如果期间发生备注、转交或结案，旧页面以 409 失败。案件转交或结案会在同一事务内删除该案件的旧授权。`cms_media_access_grants` 把授权绑定到当前负责人的会话、案件和视频；过期时间由 `CMS_PRIVATE_MEDIA_GRANT_MINUTES` 配置，默认 15 分钟。每次显式授权或续期写一条审计，播放器后续的 GET、HEAD 和单段 Range 请求只复用授权，避免把一个播放动作错误记录成许多次敏感访问。每次读取还会重新检查会话归属、当前负责人、角色/账号状态、案件目标、过期时间，以及授权人从未举报该目标。这个授权只打开 CMS 专用媒体路由，不会绕过技术验证，也不会把占位封面改成对私密封面的通用授权。

## 7. 事务、CAS 和并发

### 为什么要一个事务

“隐藏视频”不是单条更新。它至少需要：验证旧状态与权限、更新视频、追加 `moderation_actions`、追加 `audit_events`、创建系统通知。若通知写入失败而视频已经隐藏，作者会看见内容消失却收不到原因；若审计失败却状态已变，决定又无法追责。

因此每个治理命令在同一个 `BEGIN IMMEDIATE` 事务中完成，任何一步失败都回滚。

### CAS/乐观并发是什么

视频、讨论、账号、案件和申诉都有递增版本。页面把读取到的版本放入 `expectedVersion` 隐藏字段。分类、标签和删除队列任务没有整数版本列，它们用 `updated_at`/表单中的 `expectedUpdatedAt` 作同样的比较令牌。追加案件备注也要先条件更新案件版本，再在同一事务中 INSERT `case_notes`；因此它不会越过已经发生的转交、结案或另一条备注。创建操作没有旧版本；验证失败重试同时比较 `validation_failed` 状态、`validated_at` 和 `validation_started_at` 两个可空时间戳，防止一次“重试—再次失败”循环后旧页面遇到相同状态的 ABA 覆盖；删除队列重试还比较 `updated_at`。对于整数版本，提交时 SQL 同时检查 ID 和旧版本：

```text
页面读到 moderation_version = 3
工作人员甲提交，以 expectedVersion = 3 更新成功，版本变为 4
工作人员乙仍以 expectedVersion = 3 提交，影响 0 行，返回 409
```

这就是 compare-and-swap（CAS）。它不把对象长期锁给某个人，而是在写入瞬间确认“我依据的事实仍然成立”。409 要求工作人员刷新并重新判断，不能静默覆盖甲的决定。

### 申诉撤销为什么也要 CAS

撤销决定不是简单地把状态改回去。若原动作之后已有另一项治理决定，旧申诉不能覆盖新事实。系统先使用原动作保存的 `after_version` 和治理快照做 CAS；不匹配时把申诉保留为 `in_review`、设置 `has_state_conflict`，而不是自动回滚。人工处理页只允许当前复核人在“原动作前状态”与“当前后续状态”之间选择，并同时比较申诉与目标的最新版本；又有变化时仍返回 409。

## 8. 幂等、软删除和墓碑

幂等表示重复请求不会造成重复副作用。同见主要通过三层实现：

- 数据库唯一约束：每个审核动作最多一条申诉，同一举报人对同一视频或讨论最多一个未结案件。
- 状态条件与版本：旧表单重复提交得到冲突，不会再次写动作和通知。
- 队列唯一键：同一个待删文件不会因重试产生多份任务。

软删除表示记录仍在数据库中，但正常公开查询不再展示。墓碑则是软删除的一种界面语义：讨论正文不再公开，却保留节点以维持他人的回复关系。治理系统需要保留这些记录供申诉和审计，不能为了让列表“干净”就物理删除证据。

视频的作者撤回、平台移除和文件删除队列也是不同概念。CMS 的 `removed` 保留媒体供申诉；作者永久删除才会创建文件删除任务；真正 unlink 由既有队列消费者完成。但“作者点了编辑/删除”不能高于治理证据保留：目标仍非 `visible`、存在未结案件或申诉，或可申诉的隐藏/移除动作仍在 `APPEAL_WINDOW_DAYS` 窗口内且申诉未结束时，视频删除和讨论编辑/删除都被拒绝。有案件或动作历史的讨论即使没有回复也保留匿名墓碑，账号注销选项也复用这些保护。

## 9. 单一事实来源、适配器、迁移和任务队列

单一事实来源意味着每种事实只由一个权威位置表达：

- 视频技术状态仍在 `videos.validation_status`，由 validator 写最终结果。
- 视频和讨论正文仍在原表，CMS 不复制一份“后台内容”。
- 作者可见性和治理状态使用不同字段。
- 删除工作仍在 `file_deletion_queue`，CMS 只调整失败任务的下次重试时间。

`governance-store` 是适配器：它把领域命令需要的操作翻译成 SQLite 查询和事务。未来若迁移到 PostgreSQL，领域语言和 HTTP 路由可以尽量保持不变，只替换并发与查询实现。

schema v5 采用向前迁移，保留 v4 数据，并给旧内容填入安全默认值。迁移前必须制作一致备份；程序不会把 v5 自动降回 v4。备份不仅要包含数据库，还要包含视频、封面、头像及可能存在的 WAL/SHM，因此项目运维仍以完整 `data` 目录为恢复单元。

任务队列用于把“决定要做”与“真正执行外部副作用”分开。数据库先可靠记录删除任务，消费者再删除文件并处理退避。CMS 任务页只能安全地重排已有失败任务，不能冒充 worker 写完成状态。

## 10. 为什么选择 EJS、SQLite 和单体

### EJS，而不是 React-admin

同见已有 Express、EJS、CSRF 和服务端会话。CMS V1 的核心是少量高约束领域动作，不是大量可配置数据表。继续使用 EJS 可以复用安全头、表单、PRG 和部署方式，也避免为了后台引入第二套前端鉴权与通用 CRUD API。

React-admin 更适合资源很多、API 契约已经稳定、批量资料维护占主要工作的后台。若直接把治理表暴露成资源，它反而容易鼓励任意字段修改。未来如果交互复杂到值得引入前端应用，也应让前端调用领域命令，而不是跳过领域服务。

### SQLite，而不是立即迁移 PostgreSQL

当前是单机、自托管、低并发实验，SQLite 的事务、检查约束、外键、部分唯一索引和 WAL 已足以实现 V1。`BEGIN IMMEDIATE` 还能让写事务边界容易推理。

当出现多实例 Web、高写入并发、独立 worker 集群、复杂全文检索或更严格的在线迁移需求时，PostgreSQL 会更合适。迁移信号应来自真实负载和运维需求，而不是“CMS 通常用 PostgreSQL”的惯例。

### 单体，而不是立即拆服务

案件、内容状态、审核动作、审计和通知必须原子提交。把它们留在一个进程和数据库中，事务边界最清晰。过早拆服务会引入跨服务一致性、消息重复和失败补偿。

将模块分开仍然有价值：路由、权限、领域命令和存储适配器各自负责一层。未来真正需要拆分时，这些边界比现在就部署多个服务更重要。

## 11. 从 MediaCMS 和 PeerTube 学什么

[MediaCMS 官方管理员文档](https://github.com/mediacms-io/mediacms/blob/main/docs/admins_docs.md)展示了公开、私密、未列出等发布工作流，以及角色、分类、标签和异步转码任务；其[开发者文档](https://github.com/mediacms-io/mediacms/blob/main/docs/developers_docs.md)也体现了媒体处理由后台任务完成。对同见最有价值的启发是：媒体发布状态、处理状态和工作人员能力要明确分开，耗时媒体工作交给队列或 worker。

同见不直接复制 MediaCMS。它面向更完整的媒体门户，技术栈和功能范围都更大；同见现阶段不需要 Django、React、Celery、Redis、多清晰度转码或通用 REST 管理 API。复制这些组件不会自动带来案件、申诉、CAS 和审计语义。

[PeerTube 官方审核文档](https://docs.joinpeertube.org/admin/moderation)展示了用户提交带原因的报告、管理员/审核员集中处理、内部审核备注以及向举报人反馈结果等工作流。对同见最有价值的启发是：举报应进入可跟踪的处理队列，工作人员内部材料与对外反馈要分开，内容决定不能只剩一个布尔“已删除”。

同见也不复制 PeerTube 的联邦网络、远端账号、实例封锁、静音列表或自动规则生态。V1 是单站点本地治理；它需要先把本地案件、申诉、审计和隐私访问做正确。借鉴的是工作流问题和用户预期，不是照搬数据表、页面或全部功能。

## 12. 按一次真实流程阅读代码

学习这套实现时，可以沿着一次视频举报阅读：

1. 从视频页的 `POST /videos/:id/reports` 找到表单输入；`governance-routes.js` 先检查 CSRF，再同时检查登录账号和来源 IP 的单进程内存冷却，其时长由 `REPORT_COOLDOWN_SECONDS` 配置。
2. 跟到 `governance.js` 的创建举报命令，观察本人内容、可见性、说明长度和重复案件校验；再看工作人员角色提升后为什么仍以目标级举报冲突被隔离。
3. 在 `governance-store.js` 查看案件如何写入，以及数据库唯一索引如何作为最后防线。
4. 进入 `/cms/cases/:id`，观察未分配 `open` 案件如何用 `expectedVersion` 认领；视频动作也必须提交这个 `in_review` 案件的 ID，而领域服务再确认操作者仍是当前负责人。
5. 跟踪隐藏或移除命令如何在一个事务中更新事实、写 `moderation_actions`、写 `audit_events` 并创建通知。
6. 在 `/account/reports` 查看案件公开结果，再在 `/account/appeals` 查看可申诉动作和已提交申诉；两个页面都不暴露内部备注或工作人员身份。
7. 最后阅读申诉复核，观察 `pending` 申诉如何先由非原操作者优先认领为 `in_review`，以及为什么只有该复核人能提交结果。再观察撤销决定的 CAS 冲突处理。

读完后，可以用四个问题检查任何新增治理功能：谁有权执行？依据哪个旧状态？需要留下哪些公开和内部记录？部分失败或并发发生时会怎样？如果这四个问题没有清晰答案，它还不适合成为后台按钮。

## 13. V1 的边界

“可用治理版”不等于已经适合直接公开运营。V1 仍没有邮箱所有权验证、密码找回、多因素认证、完整法务流程、入口层抗滥用、监控告警、备份保留策略或事件响应体系。审核工具只能帮助工作人员一致地执行既定政策，不能替代政策制定、人员培训、法律判断和安全运维。
